---
title: "Arena allocator"
description: "GPUI’s bump-allocated storage for transient elements, exported from `gpui.rs` via `arena.rs`."
---

`gpui.rs` re-exports the `arena` module so the rest of the runtime (notably `window.rs` and `element.rs`) can share a fast bump allocator. Rather than hitting the system allocator every frame, GPUI constructs elements inside a thread-local `Arena` (`ELEMENT_ARENA`) and clears the whole thing after each draw. This keeps element creation cheap while preserving Rust’s safety guarantees via `ArenaBox`.

## Architecture at a glance

| Piece | File | Role |
| --- | --- | --- |
| `Arena` | `arena.rs` | Owns one or more fixed-size chunks and hands out aligned slices via `alloc`. Keeps a list of drop callbacks so values are properly destroyed when the arena is cleared. |
| `ArenaBox<T>` | `arena.rs` | Like `Box<T>` but tied to the arena’s lifetime. Implements `Deref`/`DerefMut`, validates access, and supports `map` for downcasting (used heavily by `AnyElement`). |
| `ELEMENT_ARENA` | `window.rs` | Thread-local `RefCell<Arena>` sized at 1 MiB; every `AnyElement::new` allocates its `Drawable` here. Cleared through the `ArenaClearNeeded` helper returned by `Window::draw`. |
| `AnyElement` / `Drawable` | `element.rs` | Wrap `ArenaBox<dyn ElementObject>` so the element tree can store heterogenous element implementations without heap churn. |

The allocator itself is intentionally simple: when you call `Arena::alloc(f)`, GPUI finds space in the current chunk, writes the value via the closure, and records a drop fn pointer. If the chunk runs out of space, a new chunk is allocated (doubling overall capacity). Calling `Arena::clear()` drops every live allocation, resets the write pointer to the first chunk, and swaps the `valid` flag that `ArenaBox` checks during derefs.

## Using the arena (internal APIs)

```rust
use gpui::{Arena, ArenaBox};

let mut arena = Arena::new(1024); // bytes per chunk
let mut value: ArenaBox<u64> = arena.alloc(|| 42);
assert_eq!(*value, 42);

// Map lets you reinterpret without copying (used for trait objects)
let mut any: ArenaBox<dyn std::fmt::Debug> = value.map(|slot| slot as &mut dyn std::fmt::Debug);
println!("{:?}", &*any); // 42

arena.clear();
// Any subsequent deref panics: ArenaBox validates `valid.get()`
```

In production code you rarely interact with `Arena` directly; instead you rely on the element APIs generated by `IntoElement`, `Render`, and `RenderOnce`. They call `AnyElement::new` which expands to:

```rust
let element = ELEMENT_ARENA
    .with_borrow_mut(|arena| arena.alloc(|| Drawable::new(my_element)))
    .map(|obj| obj as &mut dyn ElementObject);
```

GPUI collects the returned `ArenaBox` objects inside `AnyElement`, walks the tree during layout/paint, then obtains an `ArenaClearNeeded` token from `Window::draw`. The `clear()` method must run before the next frame to avoid unbounded growth:

```rust
pub fn draw(&mut self, cx: &mut App) -> ArenaClearNeeded {
    // build element tree
    ArenaClearNeeded
}

// call site
let clear = window.draw(cx);
// ... flush effects, swap buffers ...
clear.clear();
```

## Safety guarantees

- `ArenaBox::validate` panics if you try to use a value after `Arena::clear`. GPUI swaps the shared `Rc<Cell<bool>>` every time it clears, so stale handles are caught immediately (see `test_arena_use_after_clear`).
- Drops always run: `ArenaElement` stores `{ value, drop_fn }` for each allocation; `Arena::clear` drains the list, calling each drop fn in FIFO order before resetting chunks.
- Alignment is preserved: `Chunk::allocate` uses `align_offset` and `Layout` to ensure each allocation satisfies its alignment. Tests confirm this for 8-, 16-, 32-, and 64-bit integers.
- Chunk sizing: if you request an allocation larger than `chunk_size`, the allocator panics with an explanatory message. For element storage, the 1 MiB chunk chosen in `ELEMENT_ARENA` comfortably fits even large `Drawable`s.

## When to reach for the arena

- **Custom element pools**: If you build a subsystem that needs thousands of short-lived objects per frame (e.g., diagnostic overlays or debug visualizations) you can create your own `Arena` to mirror how `ELEMENT_ARENA` works.
- **Zero-copy conversions**: `ArenaBox::map` lets you reinterpret the allocation as a different trait object without moving it—handy when storing heterogeneous trait objects.
- **Deterministic cleanup**: Because `Arena::clear` runs at a known point (after each `Window::draw`), you can safely store non-`'static` references inside arena-allocated structs without worrying about cross-frame lifetime bugs.

If you only need long-lived data, stick to standard `Box`/`Arc`. But for per-frame element trees—where `gpui.rs` rebuilds the entire layout on every render—`Arena` is the key to keeping allocations predictable and fast.
